## 工夫・こだわり

### Specs First の徹底

コードを書く前に必ず `specs/ears/` に EARS 要件定義、`specs/gherkin/` に Gherkin シナリオを作成するルールを設けました。仕様未定義のまま実装を始めると「なぜこう動くのか」が後から辿れなくなる経験があったため、要件・シナリオ・実装・テストを仕様 ID（`req-XXX`, `uc-XXX`）で一貫して紐付ける **Traceability** を設計の中心に据えました。

ファイル先頭の `@see req-XXX` から Gherkin、テスト名（`test("uc-XXX: ...")`）まで一直線に辿れる状態を維持することで、仕様変更時の影響範囲を即座に特定できます。

### URL 駆動の真 SSR

検索状態を `useState` やグローバルストアではなく **URL `searchParams`** に乗せ、async Server Component で SSR する設計を選びました。これにより：

- URL 共有・ブラウザバック・リロード耐性がゼロコストで実現
- `GITHUB_TOKEN` がサーバー側から一切漏洩しない
- JS 無効環境でも最低限動作するプログレッシブエンハンスメント

を同時に達成しました。「フォーム送信 → `router.push` → SSR」という単純な流れにすることで、複雑な状態管理ライブラリが不要になりました。

### セキュリティの 組み込み

- `import 'server-only'` を API クライアントに付与しクライアントバンドル混入をビルドエラーで検出
- CSP / X-Frame-Options / HSTS 等のセキュリティヘッダーを `next.config.mjs` で全ルートに設定
- `pnpm audit` を CI に組み込み、依存脆弱性を継続監視

### AGENTS.md による AI ディレクションと MCP 活用

`AGENTS.md`（`CLAUDE.md` から参照）にプロジェクト全体の規約・原則を集約し、Claude Code がセッション開始時に自動で読み込む仕組みにしました。AI に毎回同じ指示を繰り返す必要がなく、FSD の依存ルール・仕様 ID の付け方・テスト戦略といった判断基準を一度定義すれば以降は一貫した出力が得られます。

MCP サーバーは以下を設定し、ブラウザやアプリの切り替えを最小化しました：

| MCP サーバー | 用途                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------- |
| `context7`   | Next.js / Vitest / Playwright 等の**最新**ドキュメントをターミナル内で参照。学習データの古さを補完 |
| `github`     | Issue 作成・PR 操作・コード検索をターミナルから直接実行                                            |
| `drawio`     | システム構成図を自然言語から生成（`assets/generated/`）                                            |

### 開発効率化・開発体験の向上

- **shadcn/ui + Tailwind CSS** — コンポーネントを手元に持つことで細かいカスタマイズが容易。デザイントークンと一貫したスタイリングを両立
- **es-toolkit / radash** — `lodash` より型安全で tree-shakable な関数群でユーティリティを補完
- **VSCode `settings.json`** — 保存時に ESLint 自動修正・Prettier フォーマットが走るよう設定し、「手動でフォーマットする」コストをゼロに
- **JSDoc の徹底** — 関数・コンポーネントの意図・引数・例外を明示することで、AI との協働時もコードの意味が確実に伝わる
- **FSD（Feature-Sliced Design）** — 責務ごとに層を分け、新機能追加・削除の影響範囲が層ごとに閉じる構造を維持
- **GitHub Projects + Conventional Commits** — Issue 番号をコミットメッセージに含め（例: `feat(search): ... #1`）、タスク・コミット・PR を一本のスレッドで追跡できる状態を維持

### レスポンシブ対応とアクセシビリティ

**レスポンシブデザイン** — Tailwind CSS のブレークポイントを使い、モバイル・タブレット・PC の3画面を一つのコンポーネントで対応しました。実機・DevTools で確認しています。

**アクセシビリティ** — WCAG 2.1 AA 準拠を目標に、以下を実装しました：

- `aria-label` / `aria-live="polite"` による動的更新の読み上げ通知
- `aria-busy` によるローディング状態の伝達
- `<form role="search">` 等の適切なランドマーク
- E2E テストへの `@axe-core/playwright` 組み込みによる自動検証（`uc-006-a11y.spec.ts`）

## AI の利用方法

### 流れ

| ステップ                        | ツール                                    | 目的                                   |
| ------------------------------- | ----------------------------------------- | -------------------------------------- |
| 1. 全体構想                     | Claude Opus 4.7                           | スコープ・アーキテクチャ・タスクの設計 |
| 2. UI プロトタイピング          | Claude Design                             | UIの壁打ち                             |
| 3. 要件定義・設計・開発・テスト | Claude Code / Kiro / Antigravity / Gemini | AGENTS.md で統一制御しながら実装       |

### 全体構想 — Claude Opus 4.7

全体構想の壁打ちとして Claude Opus 4.7 を利用しました。提出期限の都合上3日間での完走を目標として設定し、やること・やらないこと・タスク管理・レンダリング手法・アーキテクチャを決定しました。

### UI プロトタイピング — Claude Design

UI 設計のフェーズで Claude Design を使いました。デザインツールで0から作るより大幅に速くプロトタイプを得られた一方、生成コードはhtmlだったため、FSD アーキテクチャへのリファクタリングはClaude Codeで行いました。

### 複数 AI エージェントの活用

`AGENTS.md` に規約・原則を集約し、複数の AI エージェントが同一の判断基準で動作するよう統一制御しました。ツールを切り替えても FSD の依存ルール・仕様 ID の付け方・テスト戦略が一貫するため、出力品質のばらつきを最小化できました。

#### MCP サーバーの設定

以下の MCP サーバーを設定し、コンテキスト切り替えを最小化しました：

| MCP サーバー | 用途                                                   |
| ------------ | ------------------------------------------------------ |
| `github`     | Issue 作成・PR 操作・コード検索                        |
| `context7`   | Next.js / Vitest / Playwright 等の最新ドキュメント参照 |
| `drawio`     | システム構成図の生成（`assets/generated/`）            |

## 反省点・できなかったこと

- **コミット粒度が粗かった** — AI 生成コードをまとめてコミットする場面が多く、変更内容を細かく把握しきれなかった。本来は小単位でコミットし、すべての差分を自分でレビューしながら進めたい
- **Testing Trophy の比率が達成できていない** — E2Eテスト > Integration テスト。また、E2E テストで MSW を使えておらず実サーバーへの依存が残っている
- **Claude Code のスキルの使い分けが不十分** — `/security-review` や `/review` といったスキルをもっと早い段階から積極的に活用すべきだった
- **feature ブランチ → PR → AI レビューの流れを徹底できなかった** — ブランチを切らずに直接mainブランチにプッシュしていた
- **イシューの粒度が粗かった** — 機能単位でメインとサブの Issue に分け、設計・実装・テストをそれぞれのコメントにナレッジとして残す運用を目指したかったが実現できなかった
- **エラー発生時のアラート・通知が未整備** — pino によるログ出力は実装済みだが、Vercel 上でのアラート設定まで至らなかった
- **CHANGELOG・ドキュメントのバージョン管理がない** — バージョンアップ時に何が変わったか追跡する仕組みがなく、`conventional-changelog` 等の導入を見送った
- **モノレポ構成の検討不足** — 今回はシングルリポジトリにすべてを同居させたが、アプリ・テスト・スペックを分離するモノレポ構成のほうがディレクトリの見通しがよかった可能性がある

## 良かった点

- **Lighthouse のアクセシビリティ・ベストプラクティスのスコアが 100** — axe による E2E 自動検証と aria 属性の丁寧な付与が効いた結果
- **EARS + Gherkin による仕様駆動開発を実現** — 実装前に要件と受け入れ基準を定義した
- **証跡が残る開発プロセス** — GitHub Projects でタスク管理、GitHub Discussions で ADR を記録し、「なぜその判断をしたか」を後から確認できる体制を整えた
- **トレーサビリティの一貫性** — 仕様 ID（`req-XXX`, `uc-XXX`）・Issue 番号・コミット・テスト名が一直線に辿れる状態を維持できた

- **Vercel の活用深化** — Analytics・Speed Insights・Edge Config など Vercel のマネージド機能を積極的に活用し、パフォーマンス計測と継続改善の仕組みを作りたい
- **コードへの深い理解とリファクタリング** — Next.js のベストプラクティス・アンチパターンを体系的に学び、現在の実装を振り返って改善したい
- **Testing Trophy の比率実現** — E2E テストへの MSW 導入・カバレッジ計測による Integration テストの網羅性確認を行い、Testing Trophy が描く比率に近づけたい
- **外部 API ドキュメントの PDF 保管** — GitHub Search API のバージョン更新で仕様と実装が乖離するリスクに備え、参照ドキュメントをスナップショットとして保管する運用を整えたい
