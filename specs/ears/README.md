# EARS 要件定義

EARS（Easy Approach to Requirements Syntax）でシステム要件を記述したドキュメント群。
6つのパターンとキーワードだけで、あいまいさのない要件文を統一的に表現する。

---

## 6つの基本パターン

### 1. 常時型 (Ubiquitous)

特定の条件がなく、「常に」動作すべき振る舞いを記述する。

- **キーワード**: なし（直接記述）
- **構文**: `システムは {動作} なければならない`
- **例**: システムは、現在のページ番号を URL の `page` パラメータで管理しなければならない

---

### 2. イベント駆動型 (Event-driven)

「何かが起きた瞬間」の動作を記述する。

- **キーワード**: `WHEN`（〜のとき）
- **構文**: `WHEN {トリガー} のとき、システムは {動作} なければならない`
- **例**: WHEN 検索ボタンが押下されたとき、システムは GitHub Search API にリクエストを送信しなければならない

---

### 3. 望ましくない動作型 (Unwanted Behavior)

エラーや例外系など、「もし〜なら（困る状況）」を記述する。

- **キーワード**: `IF`（もし〜なら）
- **構文**: `IF {望ましくない条件} なら、システムは {対処動作} なければならない`
- **例**: IF 検索クエリが空文字なら、システムはバリデーションエラーを表示しなければならない

---

### 4. 状態駆動型 (State-driven)

「特定の状態にいる間」の継続的な制限や動作を記述する。

- **キーワード**: `WHILE`（〜の間）
- **構文**: `WHILE {状態} の間、システムは {動作} なければならない`
- **例**: WHILE 検索中の間、システムはローディングインジケータを表示しなければならない

---

### 5. オプション型 (Optional)

特定の機能や条件が存在する場合にのみ適用される要件を記述する。

- **キーワード**: `WHERE`（〜がある場合）
- **構文**: `WHERE {機能・条件} がある場合、システムは {動作} なければならない`
- **例**: WHERE URL に `q` パラメータが存在する場合、システムは初期表示時に検索を自動実行しなければならない

---

### 6. 複合型 (Complex)

複数のキーワードを組み合わせた条件下にのみ適用される要件を記述する。

- **キーワード**: `WHILE` / `WHERE` / `IF` / `WHEN` の組み合わせ
- **構文**: `WHILE {状態} の間、IF {条件} なら、WHEN {トリガー} のとき、システムは {動作} なければならない`
- **例**: WHILE 認証済みの間、IF レート制限残数が 10 以下なら、WHEN 検索が実行されたとき、システムは警告メッセージを表示しなければならない

---

## ID 体系

`req-{nnn}-{domain}` 形式。各ファイル内の個別要件は `req-{nnn}-{seq}` で識別する。

例: `req-001-005`（検索機能の5番目の要件）
